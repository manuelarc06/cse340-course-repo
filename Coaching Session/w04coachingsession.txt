### Topic 2: Forms for Updates (EJS + pre-filled forms)
Now let’s move to update forms, where things usually get a bit trickier.
Here’s a typical EJS edit form:

```ejs
<!-- views/categories/edit.ejs -->

<form action="/categories/<%= category._id %>?_method=PUT" method="POST">
  <label for="name">Category Name</label>
  <input
    type="text"
    id="name"
    name="name"
    value="<%= category.name %>"
  />

  <button type="submit">Update Category</button>
</form>
```

This introduces:

* pre-filling values from the database
* using `_method=PUT` for RESTful routing
* ensuring the correct entity is being edited

**One question for you:**
When you build update forms like this, what do you find more challenging — correctly pre-filling the form with existing data, or making sure the update request targets the correct record?

Me
In my case, I find it more challenging to make sure the correct record is being updated rather than filling in the form with existing data. Showing existing data in the form is usually straightforward because I already fetch the category from the database using its id and pass it to the EJS view, so I can display the current values easily. The more difficult part is making sure the correct category_id is sent back in the request and that the route updates the right record in the database. I need to carefully check that the route parameter matches the id used in the update query.

AI
That’s a very real pain point in CRUD apps, and it usually shows up when the “plumbing” between route → form → controller isn’t fully aligned.
A useful way to think about it is: there are **three identity sources** that must stay consistent:
* the URL (`/categories/:id`)
* the form action (`action="/categories/<%= category._id %>..."`)
* the update query (`findByIdAndUpdate(req.params.id, ...)` or similar)
If any one of those drifts, you get either no update or worse — updating the wrong record.
A simple pattern that helps reduce mistakes is to treat the route param as the *single source of truth*, and avoid relying on hidden inputs unless absolutely necessary.
Example update handler:

```js id="updcat1"
router.put("/categories/:id", async (req, res) => {
  const { id } = req.params;
  const { name } = req.body;

  await Category.findByIdAndUpdate(id, { name });

  req.flash("success", "Category updated");
  res.redirect("/categories");
});
```

And then ensuring your form **only needs to hit the correct URL**, not carry identity in multiple places.

### Topic 3: Sessions and Flash Messages
Now let’s shift to sessions and flash messages, since you’ve already been using `req.flash()`.
Here’s a typical setup:

```js id="sess1"
import session from "express-session";
import flash from "connect-flash";

app.use(
  session({
    secret: "mySecretKey",
    resave: false,
    saveUninitialized: false,
  })
);

app.use(flash());

app.use((req, res, next) => {
  res.locals.success = req.flash("success");
  res.locals.error = req.flash("error");
  next();
});
```

And usage:

```js id="sess2"
req.flash("success", "Category updated successfully");
return res.redirect("/categories");
```

This pattern is used to pass temporary messages across redirects.
**One question for you:**
In your own understanding, what problem are sessions solving in your app that you *couldn’t easily solve* with just `res.render()` or query parameters?

Me
In my app, I use flash messages to show feedback to the user after a redirect, for example after creating or updating a category. This is something that I could not easily do with res.render() because redirects create a new request, so any data passed directly in the response would be lost. Compared to query parameters, sessions are also more secure and cleaner because the messages are stored server-side and are not exposed in the URL.

AI
That’s a solid understanding. You’ve correctly identified the key constraint: **HTTP redirects create a brand-new request**, so anything only attached to the previous response is gone unless you persist it somewhere.
And you also picked up an important tradeoff: sessions keep things server-side, which avoids URL pollution and reduces exposure of user-facing state.
One small refinement to deepen your mental model:
Flash messages are specifically a *“one-request persistence mechanism built on top of session storage”*. So they’re not just “session data” — they’re designed to be automatically cleared after being read once, which is why they’re perfect for redirect flows.

### Topic 4: Server-side Validation
Now let’s move to validation, which connects directly to your earlier `req.body` debugging experience.
Here’s a typical server-side validation example:

```js id="val1"
router.post("/categories", async (req, res) => {
  const { name } = req.body;

  const errors = [];

  if (!name || name.trim() === "") {
    errors.push("Category name is required");
  }

  if (name && name.length > 50) {
    errors.push("Category name must be under 50 characters");
  }

  if (errors.length > 0) {
    req.flash("error", errors.join(", "));
    return res.redirect("/categories/new");
  }

  await Category.create({ name: name.trim() });

  req.flash("success", "Category created successfully");
  res.redirect("/categories");
});
```

This is basic but important:

* validation happens on the server (not just frontend)
* errors are collected, not thrown immediately
* user is redirected with feedback

**One question for you:**
In your current project, how do you decide what *must* be validated on the server side versus what you rely on the frontend (HTML or client-side validation) to enforce?

Me
In my project, I always treat server-side validation as the main layer of validation, and I do not fully rely on frontend validation. On the frontend, I use basic HTML validation like required and maxlength to help users avoid simple mistakes and improve the user experience. However, on the server side I use express-validator to enforce the real rules, such as checking that the category name is not empty and that it has a valid length. This is important because users can bypass frontend validation.
